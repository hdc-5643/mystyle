## 技术评估：「下拉挂载到父页面」方案（用户贴 cnblogs 文章询问）

用户提问：https://www.cnblogs.com/lovable/p/7122411.html 对「Power BI 可视化对象下拉挂载到父级别页面」是否有帮助。

**文章实际内容**：2017 年老文，讲通用 web 开发中 iframe 子页面通过 `jQuery("#msgs", window.parent.document)`
跨 iframe 操作父页面 DOM 实现遮罩弹层。场景是 ASP.NET 后台管理（List.aspx/Edit.aspx），**父子页面都是作者自己的**。

**评估结论：对 PBI 自定义视觉场景无效**（三条理由）：
1. **前提不成立**：文章前提是父子页面都由你控制；PBI 场景父页面是 PBI 自己的画布，
   往其内部 DOM 挂元素属入侵未公开内部结构，不受支持且随时会因 PBI 更新而崩。
2. **技术上大概率被拦**：`window.parent.document` 要求同源。PBI 自定义视觉跑在 **sandboxed iframe** 内
   （本项目已实测：DOM 链止步于 `html.visual-sandbox`，见 SKILL.md 第 201/270 行），
   sandbox 若无 `allow-same-origin` 会直接抛 SecurityError。
3. **目标不同**：文章做的是全屏遮罩（`position:fixed` 父页面层级），不是「下拉贴着触发器」。

**唯一相关场景**：Power BI Embedded —— 自建 web 应用用 `powerbi-client` 嵌入报表时，父页面才是自己的。
可行架构：视觉点触发器 → postMessage 发屏幕坐标 → 父页面自己渲染下拉（可盖住整个报表）→ 回传结果 → 视觉下发筛选。
代价：仅限自建嵌入场景，PBI Desktop/Service 无效，且需同时维护视觉与父页面两端代码。

## 【用户反馈 · 重要】我「思维固化」，把已知有效的方案漏掉了

用户批评：「你现在思维固化了，困在失败的记忆里了，需要尝试」。**这是对的，且比用户说的更严重。**

**事实**：我在总结时断言「Portal / Top Layer / z-index / openModalDialog 四种方案全部证伪，下拉浮不出 iframe 是硬限制」——
但**我自己项目的 CHANGELOG 里就记着反例**：v2.3.1.0 用过原生 `<select>`，原文：
「下拉面板由浏览器/操作系统绘制，**可超出视觉 iframe 边界，彻底解决『下拉被视觉框截断』**」。
即：能突破 iframe 的方案我早就用过并验证过，却在总结时把它漏掉了。

**原生 select 能浮到顶层的原理**（Chromium 官方设计文档《How Chromium Displays Web Pages》）：
> The select boxes must be rendered using a **native window** so that they can appear above everything else.
即下拉弹出层**不是页面 DOM**，由浏览器进程用原生窗口绘制，不受 iframe 的 `overflow:hidden` 与边界裁剪。

**v2.3.3.0 放弃 select 与裁剪无关**，纯粹是样式：`option:hover` 由 OS 渲染、CSS 不可控（只能整行变灰），
做不出「hover 只变字色」。→ **裁剪问题当年已解决，样式可控性才是唯一遗留障碍。**

**可定制 select 可能补上这个短板**：Chrome/Chromium 135+ 支持 `appearance: base-select` + `::picker(select)`，
弹出层渲染在 Top Layer 不被父容器裁剪，**且 option 可用 CSS 完全自定义**。
⚠️ 但 Top Layer 属 iframe 自身 document，**理论上仍可能被 iframe 边界裁剪**（与传统 OS 渲染路径不同），需实测。

**方法论教训（比 openModalDialog 那条更根本）**：
1. **「已证伪」的清单必须包含自己验证过的成功案例**。我犯的不是"试错不够"，是**归类错误**——
   把 select 的成功经验归进"历史版本故事"，没归进"iframe 限制"这个技术问题的解空间。
2. **连续失败会压缩解空间**。openModalDialog 上栽了两次之后，我下意识地把"突破 iframe"整个判了死刑，
   连已有的反例都视而不见。**每次断言"此路不通"前，先检索自己是否做过相反的成功验证。**
3. 用户让我"分析原理而不是翻历史"是对的——**先搞清楚机制，机制决定边界**；我反过来做，先翻历史再套结论。

**本次结果**：select 方案**用户最终也放弃了**（未执行、未产生任何代码改动，工作区保持干净，

## v2.5.1.0（commit `83d3076`）—— 面板宽度严格 = 触发器宽度

用户反馈：「垂直列表的宽度和触发器输入框的宽度一样」。

**根因**：v2.5.0 沿用了 v2.4.2 引入的
`width: max-content; min-width: 100%; max-width: 220px`
—— 这套组合会让面板宽度**脱离**触发器：触发器窄于内容最小宽度时面板更宽，
宽于 220px 时面板更窄。该组合当年是为防日期输入框被挤压而加，**v2.5 移除日期输入框后已无必要**。

**修法**：`.drs-panel` 改为 `width: 100%`（`.drs-body` 宽度即触发器宽度），
删掉 `min-width: 100%` 与 `max-width: 220px`。

**配套（防溢出，容易漏）**：
- `.drs-preset-grid` 由 `minmax(100px, 1fr)` 改为 **`1fr`**。
  `minmax` 的最小值会在容器窄于 100px 时把列撑到 100px 从而**溢出面板**，
  再被面板的 `overflow-x: hidden` 裁掉（表现为文字被切）。
- `.drs-preset` 加 `overflow: hidden; text-overflow: ellipsis`，窄触发器下文字省略号截断。
- `.drs-panel-inline`（极矮兜底）的 `width: auto; min-width: 0; max-width: none` 改为 `width: 100%`
  —— 那三个复位值针对的是已删除的 max-content 组合，留着反而是死代码。

**教训**：**修复可能变成下一次的病因**。`min-width:100%/max-width:220px` 在 v2.4.2 是正解，
到 v2.5 移除日期输入框后就成了问题源头。改动 UI 结构时，要回头检查此前为解决旧结构问题
而加的样式约束是否仍然成立。

未改 capabilities，GUID 不变。

## v2.6.0.0（commit `ea057a8`）—— 新增列表模式（字段唯一值多选）

用户指令：「增加个模式的选择，不做预设，直接下拉列表日期或者文本都支持」。

**功能**：格式面板「切片器模式」切换两种模式

用户确认的四项决策：**多选** / 日期显示 **YYYY/M/D** / **限高滚动+搜索框** / **需全选项+降序**。

**两个高危坑（会让功能完全不可用，且无报错）**：
1. **update() 必须按模式完全分流**。原逻辑「非介于型筛选（无 conditions）→ remove + 回默认预设」
   会误杀列表模式自己下发的 BasicFilter → 每选一次筛选就被自己的 update 清掉，表现为「选了没反应」。
2. **搜索框必须加白名单**。v2.4.3 机制是「除白名单外点击即收起」，漏加则一点搜索框面板就关，
   搜索功能形同虚设。白名单现为：触发器 + 预设按钮 + 搜索框 + 列表容器。

**TS 坑（实测踩到）**：`BasicFilterOperators` 是 const enum。
`BasicFilterOperators.Is` 当值用报 "only refers to a type"；传 `"Is"` 报 "not assignable"。
唯一解法是类型断言 `const OP_IS = "Is" as BasicFilterOperators`。
（技能文档原本记了这个坑但只写了行内断言，本次改为顶层常量复用。）

**display 与 raw 分离**：界面显示 YYYY/M/D，筛选下发 Power BI **原始值**。
用格式化字符串当筛选值会匹配不到数据。切页恢复统一转 display 再比对。

**capabilities**：新增 `mode`（枚举 preset/list）+ `listBehavior`（showSearch/showSelectAll）；
`dataRoles[0].displayName` 改「日期/文本字段」，**`name` 保持 `"Date"` 不变**（改了会让已有报表绑定失效）。

**GUID 换为 `DateRangeSlicer20260825008`**，displayName「日期区间切片器 v2.6-双模式」。
模式切换会清理另一模式的筛选（避免介于与 Is/In 语义冲突）。

## v2.8.0.2（commit d938a0a）—— 修复列表模式多列 bug

用户反馈：删除旧视觉重新导入 v2.8.0.1 后仍多列，且无缓存。

根因实锤：不是缓存/误导入，而是 v2.8.0.0/2.8.0.1 代码本身的 bug。
applyStyles() 中 `this.listEl.style.display = isList ? "block" : "none"` 把 .drs-list 的内联 display 强行覆盖为 block，导致 CSS 里 `display:flex; flex-direction:column` 完全失效。

修复：`this.listEl.style.display = isList ? "" : "none"`——空字符串移除内联覆盖，让 CSS 的 flex 单列布局生效。

产物校验（tar + .venv python）：确认 `this.listEl.style.display=e?"":"none"` 已写入，CSS 的 `display:flex; flex-direction:column; flex-wrap:nowrap` 完整保留。

教训：inline style.display 会覆盖 CSS 的 display 属性。用 JS 切换显示/隐藏时，显示状态应传 `""`（移除内联）让 CSS 生效，而不是传 `"block"` 等具体值。
